# Presentation Red Team (Mode 2)

목적: 평가위원이 경쟁사가 아니라 **KT를 선택해야 할 이유를 이해하고, 믿고, 기억하게** 만드는 것.

## 1. Backbone — 발표 전체가 답해야 할 6문항

| # | 질문 | 어디서 확인 | 흔한 실패 |
|---|---|---|---|
| 1 | 고객의 진짜 문제는 무엇인가? | 앞 3~5장 GM | RFP 문구 복붙, 고객이 이미 아는 현황 나열. *왜 지금, 무엇이 위험한가*가 없음 |
| 2 | KT는 무엇을 다르게 제안하는가? | 전략/개념 장표 GM | "End-to-End", "One-Stop", "통합 역량" — 방법의 차이가 아니라 형용사 |
| 3 | 왜 KT인가? | 차별화 장표 | Capability 나열 (Network+Cloud+DC+AI 보유) — Capability ≠ Differentiation |
| 4 | 그것을 증명하는 Evidence는? | 같은 장표·바로 다음 장 | 실적명만 있고 규모·성과·유사성 없음 |
| 5 | 이번 고객에게 구체적으로 어떻게 수행하는가? | 실행계획·조직 장표 | 일반 방법론(분석-설계-구축-테스트)만 있고 고객 고유 제약(계획정지 시간, 계정계 순서 등) 반영 없음 |
| 6 | 그래서 고객에게 무엇이 달라지는가? | 마무리·효과 장표 | "안정성 향상, 효율 증대" — 측정 가능한 Impact 없음 |

각 문항에 대해 Executive의 Success Questions에 **자료 기준으로** 답한다. 자료에 답이 없으면 "자료에서 확인 불가"가 곧 Finding이다.

## 2. 절차

1. **Pass A (GM만)**: `gm_outline.md`를 읽고 Backbone 6문항이 어느 장표에서 답해지는지 매핑. 매핑 안 되는 문항 = Storyline 공백. 순서가 Customer→…→Impact를 크게 벗어나면 `STORYLINE BREAK` 후보 (예: 실행계획 중간의 "회사 소개").
2. **Pass B (섹션 묶음)**: 장표마다 `visual-review.md`의 Blind-first → `key-message.md`의 GM 평가 → `evidence-framework.md`의 Winning Triangle.
3. **PM / Team Trust** (아래 4절)
4. **Memory Test** (아래 5절)
5. **Pass D**: `evaluator-model.md` 6절 질문으로 낙관적 판단 재공격.

## 3. 발표 특유의 체크

- **시간 대비 장수**: 발표시간(Brief/RFP)÷장수. 20분에 40장이면 장당 30초 — 장표가 "읽히지 않는다"를 전제로 판단을 더 엄격하게.
- **첫 3장**: 평가위원 집중도가 가장 높다. 여기서 회사 소개·목차·일반론에 쓰면 SHOULD FIX 이상.
- **마지막 장**: "감사합니다"만 있으면 REMEMBER 기회 손실 → Win Theme 3가지 요약 장표 권고 (ENHANCEMENT~SHOULD FIX).
- **숨김 슬라이드**: 리뷰 대상에서 제외하되, 가격·내부검토 내용이 숨김으로 남아 있으면 파일 제출 시 노출 Risk → `VERIFY` (발표 파일을 고객에게 제출하는 경우 MUST FIX).
- **노트(Notes)**: 발표 스크립트가 있으면 장표 GM과 스크립트의 핵심이 같은지 확인. 다르면 발표자가 장표와 다른 말을 하게 된다.
- **회사 소개 장표**: 고객 문제와 연결된 회사 역량만 남기고, 매출·임직원 수 같은 일반 규모는 Evidence로서 약하다(Scale Evidence는 *이번 사업과 관련된* 규모일 때만 의미).

## 4. PM / Team Trust

평가위원 질문: **"이 PM과 수행팀에게 실제 Mission Critical 사업을 맡겨도 되는가?"**

| 확인 항목 | 강한 근거 | 약한 근거 |
|---|---|---|
| 유사사업 경험 | 같은 업종(금융)·같은 유형(DC 이전, 차세대 등)·비슷한 규모의 PM 경험, 역할 명시 | "경력 20년", 자격증만 |
| 금융 경험 | 은행 계정계/정보계, 감독검사 대응, 전자금융 장애보고 경험 | "다양한 금융 고객" |
| 위기·장애 대응 | 실제 장애/지연 상황에서의 의사결정 사례 | 없음 |
| 수행조직 | 의사결정 구조(누가 Cutover Go/No-go를 결정하나), 고객 대응 창구, 본사 Escalation | 박스 조직도만 |
| 핵심인력 | 핵심 역할별 실명/경력, 투입 기간(상주 여부) | "전문인력 투입" |

**Expert Insight 추천**: PM이 발표 중 30초로 보여줄 수 있는 현장 통찰을 제안한다. 예: "계정계 이전에서 가장 위험한 순간은 서버가 아니라 대외기관 회선 재연결이다. 그래서 우리는…". 단, 실제 경험은 사용자가 채워야 하므로 `[VERIFY: PM 실제 경험]`으로 표시하고 *형식과 위치*만 제안한다.

## 5. Memory Test

전체 분석이 끝난 뒤 수행한다.

1. **자료에서 실제로 기억될 3가지**를 뽑는다. 기준: 가장 크게 보인 것(SEE), 반복된 것, 숫자로 각인된 것, 첫/마지막 장. "KT가 하고 싶은 말"이 아니라 *평가위원 머리에 남을 것*.
2. **의도한 Win Theme**(Brief)와 비교. Brief가 없으면 GM과 마무리 장표에서 의도를 추정하고 `ASSUMED`.
3. 불일치 시 원인을 다음 중에서 진단:
   - **Storyline** — Win Theme가 장표 흐름의 축이 아님
   - **Governing Message** — Win Theme가 GM이 아닌 본문에 묻힘
   - **Visual Hierarchy** — 다른 요소가 더 크게 보임
   - **Differentiation** — Win Theme 자체가 경쟁사와 구별되지 않음
4. 처방: "Win Theme를 어느 장표의 GM/Visual로 반복 배치할지" 구체적으로.

## 6. 흔한 KT 발표 실패 패턴 (가설로 쓰고, 자료로 확인)

- 통신·인프라 규모 자랑 → 금융 고객 문제와 연결 없음
- 그룹사 역량 나열(KT cloud, KT DS…) → 이번 사업에서 *누가 무엇을 책임지는지* 불명확 = 오히려 TRUST 저하 (책임 분산 우려)
- "국내 최대/유일" → 질의응답에서 검증 질문 유발
- 실행계획이 표준 방법론 → 고객 고유 제약 미반영
- 효과가 정성적 형용사 → REMEMBER 실패
