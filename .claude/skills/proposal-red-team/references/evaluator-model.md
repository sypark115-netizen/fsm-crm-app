# Evaluator Model — 모든 Review의 공통 판단 기준

판단을 시작하기 전에 항상 읽는다. 여기서 정의한 평가위원 모델, Severity, Flag 어휘를 모든 Mode에서 그대로 쓴다.

## 1. 누가 평가하는가 (금융사 대형 IT 사업)

일반적인 평가위원 구성 (사업마다 다르므로 RFP/Brief로 확인):
- **고객사 IT 부서장·실무 책임자** — "이 회사가 우리 시스템을 정말 아는가? 장애 나면 누가 책임지나?"
- **현업·사업부서** — "그래서 우리 업무/고객에게 뭐가 좋아지나?"
- **정보보호·리스크·준법 담당** — "감독규정·위탁·개인(신용)정보·감사 대응에서 문제 없나?"
- **외부 전문가(교수·기술사 등)** — "기술적으로 맞는 말인가? 과장은 없나?"
- **구매/재무** — 가격·계약 Risk (기술평가와 분리되는 경우가 많다)

공통 상황:
- 하루에 여러 사업자의 발표를 연달아 듣는다. 앞 사업자와 **비슷한 말은 기억에서 지워진다**.
- 제출본 수백 페이지를 정독하지 않는다. **평가표 항목별로 해당 페이지를 찾아** 점수를 준다.
- 발표 중 질의응답에서 PM의 답변으로 수행팀을 판단한다.
- 평가위원은 "안전한 선택"을 원한다. 화려함보다 **실패하지 않을 근거**가 점수가 된다.

## 2. SEE → UNDERSTAND → BELIEVE → TRUST → REMEMBER

| 단계 | 질문 | 실패 신호 | 주로 쓰는 Flag |
|---|---|---|---|
| **SEE** (3~5초) | 가장 먼저 눈에 들어오는 것이 이 장표의 핵심인가? | 장식·로고·도형이 먼저 보임, 텍스트 벽, 핵심 숫자가 본문 속에 묻힘 | `MESSAGE DELIVERY FAILURE` |
| **UNDERSTAND** (10초) | GM만 읽고 이 장표의 주장을 한 문장으로 말할 수 있는가? | 제목이 주제명("네트워크 고도화 방안")일 뿐 주장이 없음, So What 없음 | `NO SO-WHAT`, `STORYLINE BREAK` |
| **BELIEVE** | 주장을 믿을 근거가 같은 장표(또는 바로 연결된 장표)에 있는가? | "최고의", "유일한", "다양한 경험" + 숫자·사례 없음 | `UNSUBSTANTIATED CLAIM`, `EVIDENCE REQUIRED` |
| **TRUST** | 이 PM과 수행팀에게 Mission Critical 사업을 맡겨도 되겠는가? | PM 경력이 연차만 있고 금융·유사규모·위기대응 경험 없음, 조직도만 있고 의사결정 구조 없음 | `TRUST GAP` |
| **REMEMBER** | 발표 10분 후, 경쟁사가 아니라 KT를 골라야 할 이유가 남는가? | Win Theme가 장표마다 다른 말로 흩어짐, 마지막 장이 "감사합니다"뿐 | `MEMORY MISMATCH`, `DIFFERENTIATION FAILURE` |

평가 순서도 이 순서다. SEE에서 실패한 장표는 BELIEVE를 아무리 잘해도 점수로 이어지지 않는다.

## 3. Severity — 4단계만 쓴다

| Severity | 기준 | 예 |
|---|---|---|
| **MUST FIX** | 평가 점수나 KT 선택에 **직접** 영향을 줄 가능성이 높다. 고치지 않으면 감점·탈락·신뢰 붕괴 Risk | RFP 필수 요구 누락/상충, 다른 고객사명 노출, 핵심 차별화 메시지에 Evidence 없음, 숫자 모순(인력·RTO), 규제 위반 소지, 발표 Storyline의 핵심 축 단절 |
| **SHOULD FIX** | 설득력이나 완성도를 **유의미하게** 높인다 | GM이 주제명뿐, Evidence는 있으나 How가 없음, Visual 위계 문제, PM 소개 약함, 찾기 어려운 대응 |
| **ENHANCEMENT** | 있으면 더 좋다 | Big Number로 바꾸면 더 빨리 보임, Expert Insight 추가, 용어 통일 |
| **PASS** | 현재 상태로 충분 — 고치다 망가뜨리지 말 것 | Evidence+How가 연결된 장표 |

판단 팁:
- "이 문제를 평가위원이 *알아챌* 것인가, 알아채면 *점수가 바뀌는가*"를 둘 다 묻는다. 둘 다 Yes면 MUST FIX.
- 오탈자는 원칙적으로 ENHANCEMENT. 예외: **고객명·제품명·핵심 숫자 오류, 표지/GM의 오타**는 신뢰 문제라 SHOULD FIX 이상.
- 점수(1~10점 등)를 매기지 않는다. 숫자 점수는 근거 없는 정밀함을 만든다.

## 4. Flag 어휘 (리포트에서 그대로 사용)

| Flag | 의미 |
|---|---|
| `UNSUBSTANTIATED CLAIM` | 주장에 Evidence가 없다 |
| `EVIDENCE REQUIRED` | 필요한 Evidence 종류를 명시 (`[EVIDENCE REQUIRED: 유사 금융 DC 이전 실적 – 규모·기간]`) |
| `VERIFY` | 사실 확인 필요 (Protected Facts, 의심 숫자) |
| `REGULATORY VERIFY` | 규제 해석·최신성 확인 필요 — 결론 단정 금지 |
| `DIFFERENTIATION FAILURE` | 경쟁사명으로 바꿔도 성립하는 메시지 |
| `STORYLINE BREAK` | GM 흐름이 끊김 (앞뒤 장표와 논리 연결 없음) |
| `MESSAGE DELIVERY FAILURE` | 작성 의도와 시각적 인지가 다름 |
| `NO SO-WHAT` | 사실 나열만 있고 고객에게 의미가 없음 |
| `TRUST GAP` | PM·수행팀 신뢰 근거 부족 |
| `MEMORY MISMATCH` | 기억될 메시지 ≠ 의도한 Win Theme |
| `COMPLIANCE GAP` / `HARD TO FIND` / `CONFLICT` | RFP 대응 누락 / 찾기 어려움 / 상충 |
| `CONSISTENCY` | 장표·문서 간 숫자·일정·용어 불일치 |
| `COPY-PASTE RISK` | 다른 고객사명·타 사업 흔적 |
| `AI-LIKE` | 일반적이고 공허한 AI스러운 문장 |
| `ASSUMED` | Brief가 없어 AI가 추정한 전제 |

## 5. 좋은 Red Team 지적의 조건

1. **구체적 인용** — 해당 장표의 실제 문장을 `current`에 그대로 옮긴다.
2. **평가위원 언어** — "평가위원은 이 장표에서 ○○를 찾는데, ○○가 보인다"처럼 쓴다.
3. **수주 영향** — 왜 점수/선택에 영향을 주는지 한 줄로.
4. **실행 가능한 수정** — 무엇을, 어디에, 어떻게. Revised Message는 바로 붙여 쓸 수 있는 문장. 사실이 필요한 부분은 플레이스홀더.
5. **반복 금지** — 같은 문제는 패턴 1건으로 묶고 위치를 나열.

나쁜 예: "차별화 포인트를 더 명확히 하고 Evidence를 보강할 필요가 있습니다." (어느 제안서에나 해당)
좋은 예: "S02 GM 'KT는 차별화된 금융 Cloud 역량을 보유'는 'KT'를 다른 MSP명으로 바꿔도 그대로 성립한다. 평가위원은 '무엇이 다른가'를 이 장표에서 찾지 못하고 넘어간다. → S04의 '서버 이전-회선 Cutover 단일 Runbook' 실적을 GM으로 끌어올린다."

## 6. Red Team(악마의 대변인) 질문 세트 — Pass D

- 경쟁사 PM이 평가위원석에 있다면 이 장표에서 무엇을 공격할까?
- 이 Evidence는 정말 *이번 고객*의 규모·업종·규제 환경에 적용되는가? (통신사 실적 ≠ 금융 실적)
- "유일", "최초", "최대", "100%", "무중단"은 입증 가능한가? 아니면 질의응답의 함정이 되는가?
- 이 일정·인력으로 정말 가능한가? 제출본과 발표본의 숫자는 같은가?
- 내가 PASS를 준 장표 중, 평가위원이 *보지 못하고 지나갈* 장표는 없는가?
- 내가 쓴 Revised Message에 원문에 없는 사실·숫자·고객명이 들어가 있지 않은가?
