# Financial Services Cross-cutting Review

금융 고객이면 항상 적용한다. 금융 평가위원(특히 IT·정보보호·리스크 담당)은 "기능"보다 **"감독·사고·책임"** 을 먼저 본다.

## 0. 규제에 관한 원칙

- 규제·가이드라인은 개정이 잦고, 모델 지식은 낡았을 수 있다. **규제 내용을 단정하지 않는다.**
- 지적은 "이 항목을 *확인해야 한다*" 형태로 쓰고 `REGULATORY VERIFY`를 붙인다. 확인할 출처의 *이름*을 제시한다 (조항 번호·수치를 기억으로 쓰지 않는다).
- 제안서가 규제를 인용했다면, 인용이 맞는지 판단하지 말고 "인용 근거(개정일·조항)를 제안서에 명시했는가"를 본다.
- 확인 대상 출처 예 (명칭만, 현행 여부는 사용자 확인): 전자금융거래법·전자금융감독규정 및 시행세칙, 금융분야 클라우드컴퓨팅서비스 이용 가이드, 금융회사의 정보처리 업무 위탁에 관한 규정, 신용정보법, 개인정보 보호법, 금융분야 망분리 관련 개선 방안·혁신금융서비스 지정 사항, 금융분야 AI 관련 가이드라인, 금융보안원 안전성 평가·가이드, ISMS-P 등 인증 기준. 각 고객사의 내부 정보보호 규정.

## 1. 체크 질문 (도메인 공통)

| 영역 | 평가위원이 묻는 것 | 제안서에서 찾을 것 |
|---|---|---|
| 보안·개인(신용)정보 | 이전·운영 중 데이터가 어디에, 어떻게 보호되나? | 전 구간 암호화, 키 관리 주체, 접근통제·권한 분리, 마스킹, 로그 |
| 내부통제·감사 | 누가 무엇을 했는지 추적·증빙 가능한가? | 작업 승인 절차, 작업 로그·감사 추적, 변경관리, 감독검사 대응 자료 |
| DR/BCP | 사고 시 몇 시간 안에 무엇이 복구되나? | RTO/RPO 수치(RFP와 일치?), 전환 훈련 계획, 이전 중 DR 공백 대책 |
| Mission Critical 운영 | 계정계·대외계 중단 Risk를 어떻게 통제하나? | Cutover Go/No-go 기준, Rollback 계획, 대외기관 연계 테스트 |
| 위탁·외주 | 책임 주체가 명확한가? 재위탁은? | 수행 주체·그룹사·협력사 역할, 재위탁 여부, 위탁 관련 보고·승인 필요 사항 |
| 클라우드 이용 | 금융 클라우드 이용 요건을 충족하나? | 중요도 평가, CSP 안전성 평가 결과, 데이터 국내 소재, 종료(Exit) 계획 |
| 망분리·접근 | 개발·운영 접근 경로가 규정에 맞나? | 원격접속 통제, 망분리 예외 적용 근거 (`REGULATORY VERIFY`) |
| 장애 보고 | 장애 발생 시 보고 체계는? | 고객 보고·감독기관 보고 지원 체계, 연락 체계 |
| Service Continuity | KT 측 인력·조직 변동 시에도 서비스가 유지되나? | 핵심인력 교체 기준, Back-up 조직, 지식 이전 |

## 2. Severity 가이드

- RFP가 명시한 보안·DR 요구 누락/상충 → **MUST FIX**
- 규제 관련 질문에 답할 장표가 아예 없음 (예: AI 사업인데 데이터 반출·학습 데이터 통제 언급 없음) → **MUST FIX** 또는 **SHOULD FIX** (사업 성격에 따라)
- "규제 완벽 준수" 같은 근거 없는 선언 → `UNSUBSTANTIATED CLAIM` + SHOULD FIX (무엇을 어떻게 준수하는지로 바꿀 것)
- 규제 해석이 필요한 사안 → 지적 + `REGULATORY VERIFY` (Severity는 영향도로 판단)

## 3. 업권별 관점 차이 (가설 — 자료로 확인)

- **은행**: 계정계·대외계 중단 0, 감독검사, 대외기관(결제망 등) 연계
- **보험**: 대규모 계약·보험금 데이터, 레거시 전환, 설계사·채널 시스템
- **증권**: 장중 무중단, 저지연, 거래 폭주 대응, 시세·주문 계통
- **카드**: 승인계 가용성·응답시간, 부정사용 탐지, 대량 개인신용정보
- **캐피탈·저축은행**: 비용 효율, 표준화, 소규모 IT 조직의 운영 부담
- **금융공공/유관기관**: 공공 조달 규정·평가 방식, 망분리, 국산·인증 요건
